# Missing profile columns migration endpoints and error handling

The change adds three admin-gated setup endpoints to handle missing database columns that cause the `/api/profile` endpoint to hang indefinitely, plus defensive error handling in the profile endpoints to surface schema issues with actionable messages.

The infinite loading bug was caused by the production database missing columns like `ward` and `sub_county` that the ORM expected to exist. When SQLAlchemy tried to query the `users` table, the query would fail silently or hang, never returning a response. This change adds migration endpoints so an admin can fix the schema without direct database access, and wraps the profile endpoints in try-catch blocks that detect column-related errors and return a clear message pointing to the fix.

Watch for: **SQL injection gap via unparameterized text() calls** (confirmed) — the `text()` wrapper doesn't automatically parameterize SQL strings, so the raw ALTER TABLE statements are passed directly to the database. Since the SQL is hardcoded constants (no user input interpolated), this is safe in practice but violates the principle that all raw SQL should be parameterized. **Constituency column missing from migration** (confirmed) — `/api/setup/run-all-migrations` includes ward, sub_county, and county but omits constituency, which is required in profile completion checks and will still cause failures if missing.

**Verdict**: NEEDS_CHANGES

## High-level view

Three new admin-only endpoints enable self-service schema repair: `/api/setup/add-ward-column` adds all profile-related columns, `/api/setup/db-columns` lists what columns currently exist, and `/api/setup/run-all-migrations` runs both the login-tracking and profile-column migrations in one idempotent operation. All ALTER TABLE statements use `IF NOT EXISTS` for idempotency.

Both profile endpoints (`GET /api/profile` and `PATCH /api/profile`) now catch exceptions and inspect the error message for column-related keywords. When detected, they return an HTTP 500 with a message telling the user to ask an admin to run `/api/setup/run-all-migrations`.

The `text()` import was moved to the top-level imports, removing a local import that was previously inside the `/api/setup/add-login-columns` function.

The `/api/setup/run-all-migrations` endpoint is missing the constituency column that the profile completion logic checks. If a database is missing constituency, running this migration will not fix the issue.

## Three admin-gated migration endpoints

`/api/setup/add-ward-column` adds 20 profile-related columns: location fields (ward, sub_county, county, address), guardian fields, educational fields (institution, student_number, course, year_of_study, admission_year), personal fields (national_id, gender, date_of_birth), document flags (has_national_id_doc, has_student_id_doc, has_admission_letter), and financial fields (monthly_household_income, household_size). Each uses `ALTER TABLE users ADD COLUMN IF NOT EXISTS`.

`/api/setup/db-columns` queries `information_schema.columns` (PostgreSQL) or uses SQLAlchemy's inspector (SQLite/other) to list all columns in the `users` table, letting an admin verify schema state before and after migrations.

`/api/setup/run-all-migrations` combines login-tracking columns (last_login, login_count) with all 20 profile columns, running 22 migrations. Each migration is attempted individually; failures are caught and reported but don't block subsequent migrations.

All three endpoints are gated behind `require_roles("admin")`. The migration loop runs `db.execute(text(sql))` then `db.commit()` for each column; exceptions trigger `db.rollback()` and are recorded, but the loop continues.

## Constituency column missing from migration

The profile completion check requires `bool(user.constituency.strip())`, and line 475 in the diff shows constituency in the `string_fields` list, but neither `/api/setup/add-ward-column` nor `/api/setup/run-all-migrations` includes the constituency column in their migration lists. Ward, sub_county, and county are present; constituency is missing. Running the migration will not fix databases missing this column, and the profile endpoint will still fail.

## Error handling wraps profile endpoints

`GET /api/profile` and `PATCH /api/profile` wrap their operations in try-catch blocks. If an exception is raised, the error message is lowercased and checked for `'column'`, `'ward'`, or `'sub_county'`. Matches trigger an HTTP 500 with: "Database schema is outdated. Please ask an administrator to run /api/setup/run-all-migrations to update the database." The PATCH endpoint calls `db.rollback()` before raising; GET does not (correctly, since it doesn't write).

## text() import moved to top level

The diff removes a local `from sqlalchemy import text` inside `/api/setup/add-login-columns` and adds `text` to the top-level import. The new migration endpoints use `text()`, so the top-level import is required.

## SQL injection gap via unparameterized text()

The migration endpoints pass hardcoded SQL strings like `"ALTER TABLE users ADD COLUMN IF NOT EXISTS ward VARCHAR(100) DEFAULT ''"` directly to `text()`. Since the SQL contains no user input, there's no SQL injection vulnerability. However, the pattern violates the principle that raw SQL should use placeholders. If copied elsewhere with user input interpolated, it would be exploitable.

For DDL statements like ALTER TABLE, parameterization isn't applicable (table and column names can't be parameterized), so this is one of the few cases where passing a raw string to `text()` is unavoidable.

## Idempotency and rollback behavior

All ALTER TABLE statements use `IF NOT EXISTS`, making them safe to run multiple times. The migration endpoints commit each column individually; if column 5 fails, columns 1-4 remain committed. This is correct for DDL (DDL auto-commits in most databases), but it means partial migrations are possible. The response reports which columns succeeded and failed.
